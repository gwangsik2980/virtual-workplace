# 새 도구 만들기

기획서 6장의 절차(관찰 → 문제 정의 → 개선 설계 → 개발 → 업무 적용 → 검증)를 코드로 옮기는 방법입니다.

## 1. 관찰과 문제 정의

앱의 **직원 업무** 화면에서 담당자의 하루 일정을 보고 시간이 오래 걸리는 업무를 찾습니다.
**AI Tool Lab → 개선 과제 보드**에 과제를 만들고 단계별 내용을 적습니다.

후보 예시:

| 관찰한 업무 | 현재 소요 | 도구 아이디어 |
|---|---|---|
| 견적 비교 | 견적 1건당 필드 5개 수작업 | 구현됨: `quote-compare` |
| 월간 구매 실적 보고 | 월말 150분 | 구현됨: `monthly-report` |
| 발주·납기 관리 | 지연을 입고일에야 앎 | 납기 위험 알림 |
| 시장조사 | 구매 건마다 45분 | 가격 이력 통합 조회 |

## 2. 도구 슬롯 규격

도구는 `src/tools/types.ts`의 `ToolDefinition`을 따릅니다.

- `targetStage`: 도구가 연결되는 업무 단계
- `versions[]`: 버전마다 `releasedNote`와 실행 함수
- `automates`, `humanReview`, `validation`: 자동화 범위, 사람이 검토하는 지점, 검증 규칙

도구 함수는 **순수 함수**여야 합니다. 같은 입력이면 같은 결과를 내고 상태를 직접 바꾸지 않습니다.
결과를 업무에 반영하는 일은 엔진이 맡습니다. 그래야 도구가 실패해도 업무가 수작업으로 이어집니다.

## 3. 개발

1. `src/tools/<도구이름>/index.ts`에 `ToolDefinition`을 만듭니다.
2. `src/tools/registry.ts`의 `TOOL_REGISTRY`에 추가합니다.
3. 엔진에 연결합니다. 견적 비교는 `src/sim/compare.ts`의 `runComparison`이 도구를 호출합니다.
   새 단계에 붙이는 도구라면 해당 단계 처리 코드(`src/sim/purchasing.ts`의 `enterStage`, 또는 `src/sim/engine.ts`의 backlog 처리)에서
   `activeTool(state, '<도구 id>')`로 적용 여부를 확인하고 소요 시간과 결과를 바꿉니다.
4. `tests/`에 정확도 테스트를 씁니다. `tests/quoteCompare.test.ts`가 예시입니다.

### 지켜야 할 원칙 (기획서 6장)

- 추출하거나 생성한 값은 원문 근거(`source`)를 함께 남깁니다.
- 핵심 필드에는 검증 규칙을 둡니다. 실패하면 수작업으로 넘깁니다.
- 업체 선정, 계약 같은 결정은 도구가 확정하지 않습니다.
- 도구 효과를 "개선율"로 정해 두지 말고, 도구가 실제로 대체하는 작업을 계산에서 빼는 방식으로 만듭니다.
- 난수를 쓸 때는 `makeRng(seed, ...키)`를 쓰고, 키에 도구 적용 여부를 넣지 않습니다. 그래야 반사실 비교가 공정합니다.

## 4. 적용과 검증

앱의 **AI Tool Lab**에서 버전을 골라 업무에 적용하고 **효과 검증**을 실행합니다.
결과가 기대와 다르면 그것도 기록할 가치가 있습니다. 도구가 시간을 줄였지만 업체 선택은 바꾸지 못했다는 결과도 하나의 발견입니다.

## LLM을 쓰고 싶다면

현재 도구는 비용이 들지 않도록 규칙 기반으로 만들었습니다. 스캔본처럼 규칙으로 못 읽는 견적서를 처리하려면 OCR이나 LLM이 필요합니다.
그 경우 API 키가 브라우저에 노출되지 않도록 별도 서버가 필요하고 비용이 생깁니다. 시뮬레이션 재현성을 위해 LLM 결과는 캐시해서 같은 입력에 같은 결과가 나오게 해야 합니다.
